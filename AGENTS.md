# L4DS NESiCA Emulator

A server for the online services of the arcade game *Left 4 Dead: Survivors* (*LEFT 4 DEAD -生存者たち-*, L4DAC), build 1.26: the NESYS pipe service the game talks to, the ZET game server behind it, the UDP matching master, and the dedicated servers that host national rooms. The real, unmodified game is the client; the server must reproduce what the game expects byte for byte.

## Map

| Path | What |
|---|---|
| `cmd/l4ds-server` | The server a group shares: game server, matching master, room servers, database, and the endpoint shims connect to. |
| `cmd/l4ds-shim` | Stands in for Taito's NesysService on a cabinet or PC: serves the game's pipe and forwards to a server. |
| `cmd/l4ds-aio` | The all-in-one: the server and the pipe in one process. |
| `cmd/l4ds-tree` | Builds, patches, and unpatches private copies of the game ("trees"). |
| `cmd/srcds-stub` | The `srcds.exe` of a server tree: loads `bin\dedicated.dll` and calls `DedicatedMain`. |
| `internal/wire` | Byte layouts: pipe framing, startup payloads, the HTTP tunnel, and card requests and replies. |
| `internal/pipe` | The game's named pipe (Windows only). |
| `internal/nesys` | The pipe service: answers the game's NESYS commands and hands card, ranking, and HTTP requests to a `Backend`. |
| `internal/shim` | Serves the pipe with a backend (Windows only), and puts cards on the game's reader through its netcon port. |
| `internal/hotkey` | Key combinations, and system-wide keys on Windows (the shim's card keys). |
| `internal/remote` | The shim-to-server protocol: the server's HTTP handler and the shim's client, a `Backend`. |
| `internal/server` | Starts everything a server runs, for `l4ds-server` and `l4ds-aio`. |
| `internal/zet` | The game server: HTTP endpoints, card lookups, the schedule, and rankings. |
| `internal/store` | SQLite storage with ordered migrations (`PRAGMA user_version`). |
| `internal/game` | The game's rules and build 1.26's tables (levels, versus classes, and stages), checked against an install when `L4DS_GAME_DIR` is set. |
| `internal/matching` | The UDP matching master and its rooms. |
| `internal/dedicated` | The pool of dedicated servers that host rooms, watched over RCON. |
| `internal/rcon` | Source RCON client. |
| `internal/gametree` | Tree building and the byte patches, each with its reason. |
| `internal/config` | The YAML configuration (`l4ds.example.yaml` describes every key). |

## Commands

```
go build ./...
go vet ./...
gofmt -l .
go test ./...
```

`gofmt -l .` must print nothing, and `go vet` and the tests must pass on Windows. Windows-only code (the pipe, process and junction handling, and the commands that need them) sits in `_windows.go` files or behind build tags, so the module also vets for Linux (`GOOS=linux go vet ./...`); keep it that way, since the server is meant to run there too.

## Go

- Use the current language and standard library: `slices`, `maps`, iterators, `netip`, `log/slog`, and method patterns in `http.ServeMux`.
- Keep code clean, succinct, and simple. Do not build for requirements nobody has.
- Comment sparingly: a comment says why, never what. If code needs a comment to be understood, change the code first.
- Every exported identifier has a doc comment that a reader of `go doc` can act on: what it does, its units, and what zero or nil means. Facts recovered from the game binaries carry the address they came from.
- Keep packages small and their boundaries on the protocol's seams: `wire` knows bytes, not players; `nesys` reaches the backend only through its interfaces.
- Make states explicit. A type with several modes or phases gets a named state, not a meaning inferred from zero values.
- Parse input once into typed values at the edge; do not pass protocol strings deeper than the parser.
- Unknown reply fields are sent as zero or empty and listed as gaps, never guessed.
- Log every stubbed reply (`stub reply`) and every request without a handler (`unanswered request`, `unanswered command`), so gaps show while playing.

## Tests

- Arrange, Act, Assert, in that order. Act and Assert may share a line when that reads better.
- Reply layouts get golden tests once the game has accepted them.
- Fixtures use neutral data: card numbers like `7020392000000001` and invented names.

## Commits

- Small and focused, one concern each, as a single lowercase imperative headline with no body.
- No attribution lines: no `Co-authored-by` trailers and no "generated by" marks.
- Each commit builds, vets, and passes the tests on its own.

## Rules

- **Clean room.** The repository holds no game files, game text, decompiled code, or disassembly. Names, addresses, sizes, protocol values, the numbers in the game's tables, and a few original bytes at a patch site are fine.
- **Never touch an install.** Tools never modify the game folder they read from.
- **Security.** The game runs an old, vulnerable Source build, and every protocol here is unauthenticated and unencrypted. Nothing in the code, the README, or a release may suggest exposing it to the internet; supported use is closed networks and small trusted groups.
- **Machine changes need the owner.** Hosts files, certificates, and the registry are changed only by the person who owns the machine, never by a tool or an agent on its own.
- **AI use.** Contributions, including those made by agents, follow the [AI contributions policy](AI_POLICY.md).
- Keep comments and this file current with the code.
